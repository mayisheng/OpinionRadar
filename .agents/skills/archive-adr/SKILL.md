# archive-adr：把技术方案归档为 ADR

## 目的

将每次定稿的技术决策沉淀为**不可变**的 ADR（Architecture Decision Record），
确保几个月后回看代码仍能回答「为什么这样写」。规范源头是
[ADR-0001](../../../docs/architecture/adr/0001-record-architecture-decisions.md)，
本技能是它的执行 SOP，不得与 ADR-0001 冲突。

## 触发时机

- 对话中技术方案出现明确结论：用户确认「就这么定 / 按这个来」，或结论已无分歧。
- 迭代方案设计阶段（见[迭代 SOP](../../../docs/product/iteration-process.md) 第 3 步）出现 ADR 级决策。
- 用户显式要求归档 / 记录方案。
- 无需用户提醒，**定稿即归档**；归档完成后再进入编码。

## 判定：是否值得写 ADR

- **值得**：新增/替换依赖、引入/拆除一层抽象、改变部署或调度方式、
  影响数据结构或安全模型的选择、关键技术路线取舍。
- **不值得**：代码排版、命名、不改变结构的局部实现。
- 拿不准时询问用户，默认倾向于写（一篇只要求几十行，成本低）。

## 执行步骤

1. 列出 `docs/architecture/adr/` 目录，确定下一个编号 `NNNN`
   （编号只增不复用，已标 Superseded 的编号也不回收）。
2. 复制 [templates/adr-template.md](templates/adr-template.md)
   为 `docs/architecture/adr/NNNN-kebab-case.md`，文件名用英文短词概括主题。
3. 按以下要求填写：
   - 标题：`# ADR-NNNN：中文标题`
   - 日期：当天；状态默认 `Accepted`（仅当明确记录「尚未拍板」的讨论时用 `Proposed`）。
   - **背景**：为什么要决策、当前约束与触发原因。
   - **决策**：选了什么，措辞肯定、可执行；涉及代码处用相对路径链接到具体文件。
   - **备选方案**：对话中讨论过的被否路线及拒绝理由；没讨论过就不要虚构，整节省略。
   - **后果**：正面收益、引入的成本/风险、需要的配套措施（测试、限速、运维手册、文档同步）。
4. 若新决策推翻旧 ADR：新建新 ADR，并把旧文件状态行改为
   `- 状态：Superseded by ADR-NNNN`（这是唯一允许的历史改动，旧正文一字不动）。
5. 若当前处于某迭代：在 `docs/product/iterations/NNN-*.md` 的「方案要点 / ADR」小节补一行链接。
6. 篇幅控制在几十行，说清理由即可，不写成论文。
7. 完成后向用户报告 ADR 编号与文件路径；**不要自动 git commit**。

## 边界：ADR vs 迭代文档

- **ADR**：单个有分量的架构决策，长期有效、追加不改写。
- **迭代文档**（`docs/product/iterations/`）：一个迭代的目标、范围、验收标准与复盘，
  按迭代 SOP 中的模板维护，不要把迭代规划写成 ADR。

## 合规约束（撰写涉及内容采集的 ADR 时必须体现）

- 方案中不得出现录制/保存付费视频文件的设计，付费内容只做文字提取。
- 未付费充电专属内容标记「付费不可达」，不得设计任何绕过付费墙的路线。
