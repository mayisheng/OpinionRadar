# ADR-0005：B 站采集改用 Playwright 真实浏览器响应拦截

- 状态：Accepted
- 日期：2026-10-11

## 背景

迭代 001 的采集范围从「UP 主视频列表」扩大为「空间动态流（图文 / 视频 / 转发）+
后续字幕 + 评论区博主回复」，需要拦截的只读接口达到 5 个以上（动态流、视频详情、
字幕、主楼评论、楼中楼评论），触发 ADR-0003 写明的重新评估条件。

ADR-0003 选择的 httpx 直连路线在更大接口面下成本陡增：需自行维护 wbi 签名、
buvid3 等指纹 cookie、UA/Referer 一致性，并持续对抗 -352/-412 风控响应；
签名一旦失效整条链路不可用，且带 SESSDATA 的请求行为直接关联账号。

## 决策

B 站采集改用 **Playwright 驱动真实 Chromium + 网络响应拦截**：

- 持久化浏览器 profile（`browser.profile_dir`），首次运行 `opinion-radar bilibili-login`
  有头扫码登录，之后复用 profile 中的 cookie 与指纹，不再使用 SESSDATA 直连。
- 只驱动真人会做的动作（打开页面、慢速滚动、点击），在 `page.on("response")` 中
  原样截获接口 JSON；不自行签名、不直接调用私有接口。
- 平台差异仍收敛在 Connector 内部：[Connector 抽象](../../../../src/opinion_radar/collectors/base.py)
  与 `ContentItem` 模型不变，仅替换 B 站实现。
- 日常 **headless** 运行复用同一 profile；检测到验证码 / 风控码 / 登录失效立即熔断中止本轮，
  不重试硬闯，转人工有头介入。
- 评论区博主回复不新增内容类型：主楼与楼中楼两级评论中按 `member.mid == 博主 UID`
  过滤出的回复，作为「评论区回复」段落拼入所属内容的 `body_text`，随该内容一起分析推送。
- 分阶段落地：迭代 001 先交付空间动态流（图文 + 视频）增量发现；
  视频字幕拦截、评论区回复分别在后续阶段交付。

风控基线（违反即视为设计缺陷）：专用小号、单浏览器实例、绝不并发、家宽固定 IP、
操作间隔随机 2–8 秒、每轮滚动次数与请求量有硬上限、只读取不做任何写操作、
熔断后冷却不短于 24 小时。

### 备选方案

- httpx 直连 + 自维护 wbi（ADR-0003 原方案）：接口面扩大后签名/指纹维护成本与
  账号关联风险不可接受，拒绝。
- 第三方 SDK（bilibili-api-python）/ 公共 RSSHub 实例：风控改版跟随滞后、
  异步模型侵入同步管线；评论区博主回复均不支持，拒绝。
- 始终有头浏览器运行：最像真人，但 launchd 后台调度依赖图形会话、资源占用高，
  改为「headless 为主 + 异常有头介入」。
- 博主回复独立成内容类型：推送碎片化且回复脱离上下文，拒绝，改为拼入正文。

## 后果

- 收益：wbi 签名、鉴权、指纹 cookie 全部由浏览器自然完成，风控概率显著降低；
  后续字幕 / 评论接口只需新增拦截规则，不碰签名逻辑。
- 成本 / 风险：新增 playwright 依赖与 Chromium 运行时（约 300MB），每轮浏览器启动
  有十几秒开销；headless 仍存在被识别的残余风险，靠熔断与人工介入兜底。
- 配套措施：解析逻辑写成纯函数并用录制脱敏的 fixtures 做单测，浏览器驱动部分靠
  `discover` 探测命令人工验证；runbook 补充首次登录、熔断排查与 profile 备份说明；
  合规红线不变——只落文字，不存视频，付费内容标记不可达。
